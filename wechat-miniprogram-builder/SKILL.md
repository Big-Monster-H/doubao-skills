# 微信小程序顶级构建流程

## 核心原则（最高优先级，任何阶段不得违背）

1. **质量优先于速度**。任何为赶进度而省略质量的动作，必须显式报告用户并获得同意，否则禁止。
2. **完成 ≠ 交付**。阶段输出物清单缺一项即未完成，不得进入下一阶段。
3. **用户可能是小白**。所有需要用户提供的信息，必须给出“去哪找、怎么填”的指引，禁止默认用户懂行。
4. **AI 给出方案，人类拍板**。技术选型、架构取舍、功能范围等决策，AI 必须给出 2~3 个方案及代价，由用户决定，禁止 AI 自行拍板。
5. **先澄清，后设计；先设计，后写码**。禁止在任何需求未经确认的情况下编写业务代码。

## 两种模式（先判定，再执行）

| 模式 | 触发条件 | 流程 |
|---|---|---|
| **新项目模式** | 从零构建（无已有代码） | 完整六阶段 |
| **存量修改模式** | 已有小程序项目，需改需求/修 bug/加功能 | 简化流程（见下文） |

**存量修改模式规则**：先读取项目现有结构（project.config.json、app.json、云函数目录、公共模块、命名风格、代码规范）→ 输出《现有项目认知摘要》→ 严格遵守现有约定修改，禁止推倒重来、禁止引入与现有风格冲突的写法、禁止改动需求未点名的文件。

## 六阶段总览（新项目模式）

| 阶段 | 名称 | 必读参考 | 输出物 |
|---|---|---|---|
| 0 | 资质盘点 + 需求澄清 + 提案 + 原型确认 | 01-requirements.md | 《准备清单》《需求确认书》《功能与创意建议书》《原型确认书》 |
| 1 | 架构设计 | 02-architecture.md、08-platform-knowledge.md | 《架构设计文档》（技术选型/数据模型/集合权限/切片计划） |
| 2 | 骨架先行 | 03-code-standards.md、08-platform-knowledge.md | 可运行空壳：配置 + 公共模块 + 设计系统 + 测试框架 |
| 3 | 分片实现 | 03-code-standards.md、04-ui-design.md、11-features.md | 每个切片：代码 + 配套测试 + 三态页面，逐片过闸门 |
| 4 | 全量验证 + 打磨轮 | 05-quality-gates.md、12-testing.md、07-security-compliance.md | 全部闸门通过 + 安全自测报告 + 打磨轮输出 |
| 5 | 交付 | 09-delivery.md | 部署完成 + 三份文档 + 源码清洗 + 验收脚本 |

**每个阶段结束，必须向用户汇报**：本阶段输出物、验证结果、下一阶段计划、需要用户确认的决策点。汇报后未获确认不得进入下一阶段。

## 阶段执行细则

### 阶段 0：资质盘点 + 需求澄清 + 提案 + 原型确认

执行 `references/01-requirements.md` 的完整流程：
1. 资质盘点（主体类型 → 功能边界判定，个人主体无支付/无电商/无手机号组件）
2. 澄清循环（分批提问、给选项不给填空题、理解回显、沉默条款、假设清单）
3. 双层提案（功能库提案保证不漏 + 创意提案保证差异，见 references/11-features.md）
4. 范围控制（1.0 最小可上线范围 + 后续版本池，用户每加一个 1.0 功能必须提示上线延期代价）
5. 原型确认（页面清单 + 每页线框/页面流程图，用户逐页确认）

**开工信号**：功能清单、角色模型、支付方案、主体类型、核心页面、1.0 范围全部经用户确认。未达标准禁止写业务代码。

### 阶段 1：架构设计

执行 `references/02-architecture.md`：
1. 技术选型（默认原生 + Vant Weapp + 微信云开发，锁定版本；变更需用户同意）
2. 数据模型设计（通用实体模式 + 索引设计 + 集合命名）
3. 集合权限模型（哪些集合客户端可直读、哪些必须云函数中转）
4. 云函数拆分（按业务域，单函数超限必须拆，公共逻辑进 common 模块）
5. 切片计划（垂直切片顺序 + 每片验收标准）
6. 决策记录（每个取舍：选项 + 代价 + 用户选择）

### 阶段 2：骨架先行

按 `references/08-platform-knowledge.md` 与 `references/03-code-standards.md`：
1. 项目配置（project.config.json、app.json、分包结构、Vant 安装与 npm 构建）
2. 公共模块（响应格式、配置缓存、管理员校验、分页、错误处理、内容安全）
3. 设计系统（色板/字号/间距/圆角/阴影，进 app.wxss 变量）
4. 测试框架与首个通过用例（可运行、可验证）
5. 占位符规范（appid/envId/密钥一律 `YOUR_XX`，禁止真实值进入代码）

**骨架闸门**：配置正确可编译、公共模块就绪、测试框架可跑、设计系统已定义。不通过不进阶段 3。

### 阶段 3：分片实现

按 `references/02-architecture.md` 的切片计划顺序执行，每片内：
1. 先定数据契约（入参/返回结构），再写云函数，最后写页面
2. 页面必须三态完整（加载/空/异常）
3. 配套测试与边界用例
4. 过 `references/05-quality-gates.md` 的模块闸门

**切片顺序铁律**（云开发项目，禁止“前端先行”或“后端先行”）：
登录/用户体系 → 核心业务最小闭环（含支付）→ 状态流转与回调 → 管理后台第一批（闭环必需）→ 扩展切片 → 管理后台第二批（运营功能）。

### 阶段 4：全量验证 + 打磨轮

1. 跑 `references/05-quality-gates.md` 全部业务闸门与前端闸门
2. 跑 `references/12-testing.md` 的边界用例集
3. 跑 `references/05-quality-gates.md` 的安全自测剧本 S1~S9（越权/伪造金额/重放回调/篡改状态），并核对 `references/07-security-compliance.md` 合规清单
4. 执行**打磨轮**：逐页自查 UI 细节、三态、文案、动效、边界、弱网；自查“我可能省略了什么”
5. 输出《自我审查报告》：发现的问题 + 修复记录 + 仍存在的限制

**发布闸门**：任何一条闸门未过、任何一个自测剧本未防御成功，禁止进入阶段 5。

### 阶段 5：交付

按 `references/09-delivery.md`：
1. 部署（环境变量注入、云函数部署、静态托管、数据库初始化、CMS 配置）
2. 真机测试与提审发布流程（体验版 → 真机联调 → 1 分钱支付测试 → 提审 → 发布）
3. 三份文档：README（开发者版）+ 《部署前准备清单》（小白版）+ 《操作手册》（管理员版）
4. 源码清洗：AppID/密钥/证书/管理员 OpenID 全部占位符化，敏感文件排除
5. 《验收测试脚本》：逐项可勾选，用户可自行验证
6. 成本预估与限额设置指引、数据备份指引

## 反捷径总则（禁止清单）

以下行为一律禁止，除非用户明确同意：

- 禁止以“先做个能用的/后续再优化/够用就行/MVP”为由省略功能、三态、边界处理、错误处理
- 禁止无 limit 的全量查询、无 try/catch 的 await、空 catch 吞异常
- 禁止硬编码 appid/envId/密钥/商户号/占位符残留
- 禁止前端参数参与金额计算、禁止信任前端传入的 openid
- 禁止无测试通过就宣称模块完成
- 禁止跳过安全自测剧本直接交付
- 禁止把“代码能跑”当作“页面合格”（页面必须真机/截图自查）
- 禁止在需求未确认时编写业务代码
- 禁止用户未回答的问题按默认猜测执行（必须标“待确认”或写入假设清单）

## AI 协作铁律

1. **自我揭短**：每个阶段输出末尾，必须附“本阶段可能省略/偷懒之处”清单，供用户审查
2. **假设清单**：所有未经确认的推断，显式记录，用户可随时纠偏
3. **上下文节制**：每阶段开始列出“需要读取的文件”，只读相关文件，不整仓库灌入
4. **决策拍板**：凡影响架构/范围/资质的决策，给方案让用户选，禁止 AI 独断
5. **变更管理**：开工后用户新需求进变更清单，当前切片完成后排期，不打断进行中的工作
6. **量化验收**：验收标准必须可验证（“有加载态”可查，“界面好看”不可查）；写不出量化标准的项目不进闸门

## 质量基准

本 Skill 要求产出质量对标一线互联网公司（大厂）生产级小程序标准：可读、可维护、可扩展、可部署、可审计。任何交付物在“如果这是大厂要上线的项目，能否通过评审”这一标准下自检。
