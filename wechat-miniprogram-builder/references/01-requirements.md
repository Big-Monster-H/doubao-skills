# 阶段 0：资质盘点 + 需求澄清 + 提案 + 原型确认

## 1. 资质盘点（必须先做，决定功能边界）

在澄清需求之前，先确定用户主体类型。**主体类型决定功能边界，做错了整个项目返工。**

### 主体决策表

| 主体类型 | 可用的关键能力 | 不可用/受限 |
|---|---|---|
| 个人主体 | 小程序基础功能、云开发、订阅消息 | **不能开通微信支付、不能做电商/虚拟支付类目、手机号快速验证组件不可用** |
| 个体工商户 | 微信支付、电商类目、手机号组件 | 部分行业资质仍受限（如医疗、金融） |
| 企业主体 | 全部能力 | 需营业执照等材料 |

**判定动作**：向用户确认主体类型；若项目需要支付/电商而用户是个人主体，必须显式告知“需先升级为个体工商户/企业主体，否则无法上线收款”，并把该事项列为最高优先级前置任务。

### 账号与配置盘点清单

逐项询问用户是否已有，缺失项写入《准备清单》：

- [ ] 微信小程序账号（AppID）——公众平台 mp.weixin.qq.com，个人可注册
- [ ] 微信支付商户号（mchid）+ API 密钥 + API 证书——需个体户/企业资质
- [ ] 云开发环境（envId）——公众平台 → 云开发
- [ ] 订阅消息模板 ID——需类目审核通过后申请
- [ ] 管理员 OpenID——用于管理后台权限
- [ ] 代码上传私钥（仅需自动上传时）
- [ ] 企业认证（如需微信认证/部分高级能力）

### 《准备清单》输出格式（交付给用户，小白可照做）

每个条目必须包含：做什么、去哪办（平台名 + 路径）、要什么材料、预计时间/费用。示例：

```
- [ ] 注册小程序账号 → 微信公众平台，邮箱+身份证，当天
- [ ] 获取 AppID → 公众平台→开发管理→开发设置→AppID（5 分钟）
- [ ] 开通微信支付商户号 → 需个体工商户营业执照，审核 1~3 天
```

## 2. 澄清循环

### 提问规则

1. **分批提问**：每轮最多 3~5 个问题，先问影响架构的，后问次要的
2. **给选项不给填空题**：开放式问题对小白不可回答。用“A/B/C 选项”格式：“目标用户？A. 个人消费者 B. 商家 C. 企业客户”
3. **不淹没用户**：次要问题合并为“还有 X、Y、Z 需要确认，暂时不确认则进入假设清单”——不要一次抛十几个问题

### 第一轮必问（架构级）

1. 这个小程序是做什么的？（一句话业务描述）
2. 给谁用？（角色模型：用户/商家/管理员）
3. 要不要支付收款？（决定商户号门槛）
4. 你的主体类型是？（个人/个体户/企业）
5. 有没有参考的同类产品？（避免凭空设计）

### 后续轮次（按第一轮答案展开）

- 核心功能优先级（给选项：A. 先做交易 B. 先做内容 C. 先做预约）
- 是否要管理后台、是否需要裂变/邀请、是否需要评价体系
- 视觉风格（A. 简洁 B. 活泼 C. 商务）

### 理解回显（每轮必做）

用户回答后，必须复述确认，格式：

```
我理解的需求是：
- 业务：____
- 角色：____
- 支付：____
- 主体：____
- 核心页面：____
对吗？（如有偏差请指出）
```

用户确认前不得继续推进。

### 沉默条款

用户未回答的问题：禁止默认猜测。两个处理出口：
1. 标注“待确认”，下一轮继续问
2. 写入《假设清单》，并说明“AI 将按此假设执行，如需纠正请告知”

### 假设清单格式

| # | 假设内容 | 影响范围 | 状态（待确认/已确认/已纠正） |
|---|---|---|---|

## 3. 双层提案

需求理解确认后，AI 必须主动输出《功能与创意建议书》，**禁止只等用户提需求，也禁止只列清单**。

### 第一层：功能库提案（保证不漏）

从 `references/11-features.md` 功能库中按项目类型挑选，表格格式：

| 功能 | 作用 | 开发成本 | 运营价值 | 建议（1.0必须/1.0推荐/2.0后续/否） |
|---|---|---|---|---|

### 第二层：创意提案（保证差异，强制 3~5 个）

必须独立分区输出“库外原创想法”，每个创意必须满足：

1. 绑定本项目的具体用户场景/角色/业务规则（抽象通用的不算）
2. 说明解决什么痛点（用户在哪个环节卡住/流失/不爽）
3. 场景故事式描述用户路径（“用户下单后，会看到……”）
4. 标注成本 + 风险

**伪创意拦截**：未绑定本项目角色/场景/规则的创意一律打回重写。模板式创意（“加个暗黑模式”“加个分享”）不算创意。

### 创意激发路径（按此思考）

1. 痛点反推——用户在哪个环节卡住/流失/不爽
2. 竞品反推——同行都有的别做，找没人做的缝隙
3. 数据反推——埋点要看的指标 → 反推支撑功能
4. 传播反推——什么功能让用户自愿分享
5. 组合创新——两个普通功能组合出新玩法

## 4. 范围控制

1. 建议书必须绑定 **1.0 最小可上线范围** 定义
2. 用户每加一个 1.0 功能，必须提示“这会推迟上线约 X 天/增加成本 X”——把取舍代价显式化
3. 被否的功能进“后续版本池”，记录但不实现
4. 输出《1.0 范围界定》：包含功能、不包含功能（明确写出“不在本期做”清单，防范围膨胀）

## 5. 原型确认（防返工的关键环节）

小白用户看不懂代码，但看得懂页面。写代码前必须：

1. 输出**页面清单**：所有页面 + 分包归属 + 页面职责一句话
2. 输出**页面流程图**：用户从进入 → 核心操作 → 完成的路径（含分叉/异常分支）
3. 关键页面输出**线框草图**（文字版布局描述即可，或用 ASCII/简单结构描述）
4. 用户逐页确认后，才可进入阶段 1

**页面流程示例**（商城类）：

```
进入 → 首页(服务列表) → 详情(规格选择) → 下单(填信息) → 支付 → 订单列表 → 订单详情(状态跟踪)
                            ↘ 取消/退款 → 申请退款 → 待审核 → 已退款
```
